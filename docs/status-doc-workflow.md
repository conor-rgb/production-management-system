# Status-sheet workflows in the production hub

Updated 16 September 2026. [Current plan](production-hub/PLAN.md); [original workflow study](archive/2026-09-16-before-direction-reset/docs/status-doc-workflow.md).

The sheets express real production needs: identity, next actions, date-specific holds, casting/location decisions, crew attendance, travel/hotels/cars, kit, catering, costs, delivery and close. Preserve those relationships and fast table work. Do not reproduce their placeholder rows, shifted setup mappings or duplicate data ownership.

The earlier proposal to add another Status Doc tab is superseded by consolidation around one project workspace. Existing Status Doc/Workbook screens remain available as transitional tools until their manual-only data is mapped and their functionality covered. Merely hiding them is not a migration.

Keep global people distinct from project bookings. A booking should feed dates, crew, logistics and costs; views should not require re-entering the same person or journey. Drive provides the job's document home and published outputs. Each module should load only its required records.

Finance is first: approved estimate snapshots, stable live costs, invoices/allocations/payments and explicit close exceptions. Travel/delivery/close follow once the data ownership is sound. Working bound Apps Script generators remain until source and output parity have been verified.

For inspected live Sheets, mapping issues and PDF references see [AUDIT.md](production-hub/AUDIT.md). For implemented versus planned capability use the [release records](releases/README.md), not the old status-sheet wishlist.
